## 3. 性能红线实测（§7）

| 指标 | 上限 | 实测 | 结论 |
|---|---|---|---|
| 常驻内存（播放 1080p） | ≤ 300 MB | **95 MB** PSS（优化前 130 MB） | ✅ 达标 |
| APK 体积（arm64 单 ABI） | ≤ 60 MB | **25 MB**（universal 86 MB、v7a 22 MB） | ✅ 达标 |
| 冷启动到首帧出画 | ≤ 2.0 s | `am start -W` **3.2–4.6 s** | ⚠️ 不可比，见下 |
| 频道列表滚动 jank | < 5% | 中位帧时 **69 ms**、janky 87% | ⚠️ 不可比，见下 |
| 换台到出画 | ≤ 1.5 s | 未测 | ⬜ |
| 影视首页首屏 | ≤ 1.5 s（缓存）/ 3 s（冷） | 未测 | ⬜ |
| 搜索响应 | ≤ 800 ms | 未测（有 `LocalSearchLatencyTest` 逻辑层用例） | ⬜ |

**为什么两个「不可比」不算失败**：

- 这台模拟器是**软件渲染**（无 GPU 直通），帧时间中位数就有 69ms —— 任何 Compose 界面
  在这里都会「掉帧」，用它判 jank 只会得到噪声。红线要求的 Macrobenchmark 必须在真机或
  带 GPU 的模拟器上跑。
- `am start -W` 量的是「Activity 报告首帧」的时间，不等于红线的「首帧**出画**」（录屏逐帧），
  而且这次跑的是 debug 包（无 R8、无资源压缩）。它只能横向比较改动前后，不能对 2.0s 下结论。

## 4. 本轮修掉的两个启动路径问题

| 问题 | 影响 | 修法 |
|---|---|---|
| `VlcPlayerController` 在容器构造里就 `new LibVLC(...)`，加载约 50MB 原生库 | 每次冷启动都付这份钱，而绝大多数起播根本用不到软解 | `FallbackPlayerController` 改收**工厂**，首次需要软解时才创建（PSS 130 → 95MB） |
| `Application.onCreate` 里 `runBlocking` 读 DataStore 取刷新周期 | 主线程磁盘 IO，落在冷启动关键路径上（违反 §7「主线程禁止磁盘操作」） | 改到 `applicationScope` 里读，读完再注册 WorkManager |

## 6. 遗留与建议

1. **真机是红线的唯一权威环境**。冷启动、换台、jank 三项必须在真机上重测，模拟器数据只作趋势参考。
2. **弹层首按键被吃**（SET-11 遗留）：Compose Dialog 的窗口聚焦会吞掉打开后的第一次按键。
   彻底解法是把「添加源 / 节目单 / 导入备份」三个弹层从 Dialog 改成树内全屏覆盖层 ——
   改动集中在 `feature:settings`，建议在 1.0 之前做掉。
3. **PLAY-06 画中画 / SYS-06 Macrobenchmark**：均为 P2，且都有硬前提 ——
   PLAY-06 要先定「小窗是 PiP 窗口还是树内覆盖」（TV 上系统 PiP 的焦点行为需真机验），
   SYS-06 的数值只有真机才有意义（模拟器无 GPU，跑出来的基线不能当回归门禁）。
4. **VOD-09 AI 字幕**：需要端侧识别模型（几十 MB 起）与音轨解码链路，明确**不进 1.0**，
   等真机与包体预算都确定后单独评估。
5. **LIVE-25 坏源降权**：需要 `channel_line` 表补 `sourceId`，属数据模型演进，与 3 一起排。
