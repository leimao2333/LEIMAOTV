# 发版流程（SYS-07）

发版这件事只有两个动作：**改版本号 + 打 tag**。包由 GitHub Actions 打，Release 由它建，
附件由它传 —— 人手碰不到 APK，也就没法传错文件。

```
四处同步版本号 → 提交 → 打 tag → git push 分支与 tag
                                        ↓
                        .github/workflows/release.yml
                                        ↓
              校验 / 测试 / 签名 / 按名命名 / 建 Release
```

规则本身在 `RULES.md` §10（版本号公式、四处同步、发版清单），这里只讲**怎么操作**。

---

## 一、密钥（只在第一次做）

密钥与签名配置**都在仓库里**，CI 不用配任何 secret。

```bash
bash scripts/create-keystore.sh      # 生成 keystore/leimao-tv.jks + keystore.properties
git add keystore/leimao-tv.jks keystore.properties
```

`.gitignore` 只放行这一个密钥文件（`keystore/*` 全排，`!keystore/leimao-tv.jks` 单独开），
别的 `.jks` 不会被人 `git add -A` 顺手带进仓库。

### 为什么密钥在仓库里

这是仓库主人的决定，好处很直接：**换台机器、换个人、重装系统，都能签出包**；
不会因为忘了配 secret 而在发版当天卡住。

代价必须知道：

- **能 clone 这个仓库的人就拥有签名能力**，可以签出一个「看起来是官方」的包。
  仓库若是公开的，风险等同于把发布权交出去。真在意就把仓库改成私有 —— 这一条比任何流程都管用。
- **密钥进过 git 历史，删文件也去不掉**（SHA 还在对象库里，随时能取）。要真正撤销，
  只能换一把新钥匙，而换钥匙意味着老用户装不上新版（见下）。
- 密码在 `keystore.properties` 里明文，同上。

想改回「签名能力只在我自己机器上」，把 `keystore/` 与 `keystore.properties` 加回
`.gitignore`，从历史里清掉（只能重建仓库或接受历史留存），
再把 `.github/workflows/release.yml` 里「确认签名材料」那一步换成从 secret 还原。

### 一条不能犯的错

**不要重新生成密钥。** Android 只认同一把钥匙续签，密钥一换，已装旧版的用户
装新版会得到 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，只能卸载重装 —— 进度、收藏、源配置全没。
`scripts/create-keystore.sh` 检测到已有密钥会直接拒绝执行，就是挡这个。

### 本地验证（可选）

```bash
./gradlew :app:assembleRelease
$ANDROID_HOME/build-tools/<版本>/apksigner verify -v --print-certs app/build/outputs/apk/release/app-release.apk
```

应当看到 `Verified using v2 scheme (APK Signature Scheme v2): true`（RULES §10.4 第 4 条）。

没有 `keystore.properties` 时 `assembleRelease` 会产出 `app-release-unsigned.apk` ——
本地能跑，但 CI 会在 `apksigner` 那一步拒发。`keystore.properties` 存在却指不到密钥文件时
构建直接失败：那种「配置写了一半」的状态最容易骗过自己。

## 二、日常发版

1. 按 `RULES.md` §10.2 定下一版号（里程碑内只动第三段；第三段走满 9 就进第四段）；
2. 四处同步（§10.3）：`app/build.gradle.kts`、`core/version/AppVersion.kt`（含 `CHANGELOG` 条目）、
   根 `CHANGELOG.md`、文档（`docs/功能清单.md` / `TODO.md`）；
3. `./gradlew test ktlintCheck assembleDebug` 自检；
4. 提交，然后打**带注解**的 tag —— 注解正文就是 Release 正文：

```bash
git tag -a v0.2.9.8 -m "这一版能干什么了：一句话讲清，写给下载的人看"
git push origin main
git push origin v0.2.9.8        # 推 tag 就是发版
```

5. 打开 Actions 看 `Release` 那条跑完，Release 页面出现两个附件：
   `leimao-tv-v<版本>-universal.apk` 与同名 `.sha256`。

`git push --tags` 也行，但如果本地攒了一堆旧 tag，逐个推更可控。

## 三、流水线做了什么

| 步骤 | 拒绝发版的条件 |
|---|---|
| 确认签名材料 | 仓库里没有 `keystore.properties`；配置里缺项；密钥文件不存在；别名或密码打不开密钥 |
| `ktlintCheck` | 风格不合规 |
| `test` | 任何单测失败（含版本号、CHANGELOG 同步测试） |
| `assembleRelease` | R8 / 资源压缩失败 |
| 校验产物 | tag 与 `versionName` 不一致；`versionCode` 不符 §10.2 公式；`CHANGELOG.md` 没有这一版条目；release 目录里 APK 不是恰好一个 |
| `apksigner` | 包没签名，或 v2 不是 `true` |
| `aapt2 dump badging` | 包名不是 `com.leimao.tv` |
| 发布后回下载比对 | 远端附件与刚签出来的包 sha256 不一致（上传截断）；下载不到会重试四次 |
| 发布 | Release 已存在时**覆盖附件**（重跑不会留下两个同名附件） |

tag 与版本号不一致这道闸是整条流水线最值钱的一步：它挡住的是「tag 打了、包也出了，
但包里是上一版的代码」—— 用户装完版本号没变，只会以为更新坏了。

## 四、排障

| 现象 | 原因与处理 |
|---|---|
| `仓库里没有 keystore.properties` | 密钥没提交，见第一节 |
| `keystore.properties 指向的密钥不存在` | `.gitignore` 没放行，或换了路径没改配置。检查 `git ls-files keystore` |
| `密钥读不出来：别名或密码与 keystore.properties 对不上` | 配置被手改过，或被换成了另一把钥匙 |
| `tag 是 vX，包里的 versionName 是 vY` | 四处同步没做全，或者 tag 打在了错误的提交上。改对版本号后删掉本地与远端 tag 重打（`git push origin <tag> --force`，并在提交信息里说明原因） |
| `versionCode 是 A，按 §10.2 公式应为 B` | 只改了 `versionName` 忘了算 `versionCode` |
| `CHANGELOG.md 里没有 vX 的条目` | 先写日志再发版（§10.5「先改版本号、日志回头补」是明确的反模式） |
| `release 目录里有 N 个 APK` | 有人开了 ABI 拆包。要么关掉，要么在 `校验产物` 那步补上「哪个包叫哪个名」的映射，别硬发 |
| `apksigner` 报 v2 不是 true | 签名配置没生效，检查 `keystore.properties` 的路径是否能被 Java 读到（Windows 上反斜杠是转义符，写正斜杠） |
| `上传后的附件与构建产物 sha256 不一致` | 上传被截断。**别手动重传**：删掉这个 Release 重打 tag 让流水线重跑 —— 手动传的附件很容易传错文件 |
| 拿本地构建的包去比对远端附件，永远对不上 | 这是正常的：本地与 CI 的产物天然不等价（v0.2.9.8 实测相差 1046 字节，签名正常）。比对只在流水线内做 |

## 五、几个刻意的取舍

**上传前不经人手。** 附件从构建目录直接进 Release，名字由脚本按 RULES §10.4 第 6 条拼出来。
应用内更新器（SET-07）按名**精确匹配**，人手改名就会让所有人收不到更新。

**只发一个包，名字是 `-universal`。** 现在没有任何 native `.so`（VLC 还没引入），
这一份包在 32 位与 64 位盒子上都能装 —— 它**就是** universal 包，按 universal 命名才诚实。

叫主名（`leimao-tv-v<版本>.apk`）不行：更新器把主名当作「arm64 专用包」，对 32 位设备只认
`-v7a` 与 `-universal`，那些盒子会永远收不到更新，而包明明是能装的。这条由
`ApkAssetsTest` 里「只有 universal 时任何设备都退到它」和「32 位设备遇到只有 arm64 包时判定没有可用包」
两条用例一起钉住。

**接入 libVLC 之后必须换成真正的 ABI 拆包**：那时三份内容才真的不同，arm64 那份才该叫主名。
流水线里「release 目录恰好一个 APK」的断言会主动失败，逼着人把命名映射补齐 —— 不会悄悄发错。

**不用 `PackageInstaller` 静默安装。** 应用自己替换自己是危险能力，装不装由系统安装界面确认。

**不做后台自动检查更新。** 更新检查（SET-07）只在用户进页面时查一次，GitHub 匿名配额够用。

**不拿本地产物当基准。** 发布后的 sha256 比对只在流水线内做：本地与 CI 构建出来的 APK
天然不逐字节相同（AGP 会写构建元数据，工具链产物也不等价）。用本地包去对远端附件，
只会得到一个永远对不上的结果，反而掩盖了这条真正要防的事 —— 上传截断。
