# 架构设计

> 目标：一个 App 里跑两套内容形态（直播 / 点播），但**共用一套播放器、一套搜索、一套焦点体系**。
> 本文只写「为什么这么分」，具体实现细节在代码里。

## 1. 分层与依赖

```
┌──────────────────────────────────────────────┐
│  :app   组装层（Activity / NavHost / DI）     │
└───────┬──────────────────────────────┬───────┘
        │                              │
┌───────▼────────┐  ┌──────────────┐  ┌▼──────────────┐
│ :feature:iptv  │  │ :feature:vod │  │ :feature:search│  ← 平级，互不依赖
└───────┬────────┘  └──────┬───────┘  └┬──────────────┘
        │                  │           │
┌───────▼──────────────────▼───────────▼───────────┐
│  :core:model   :core:database   :core:network     │
│  :core:player  :core:designsystem                 │
└───────────────────────────────────────────────────┘
```

**为什么 feature 之间禁止互相依赖**：直播板块要「搜影视」，看起来该直接调 `:feature:vod`。
但那样会把「两个板块」耦合成一个 —— 影视模块的改动会波及直播。所以跨板块的协作只走两条路：
`core:*` 里定义的接口（如 `SearchRepository`）与导航事件（路由 + 参数）。

## 2. 两个板块如何共存

| 关注点 | 做法 |
|---|---|
| **启动落点** | 冷启动直接进直播播放页（RULES §6.6）。`AppStartDestination` 在 `:app` 里算一次：合规提示未同意 → 提示页；无源 → 引导页；否则 → 播放页 + 上次频道 id |
| 模式状态 | 单例 `ModeRepository`（DataStore 持久化），`StateFlow<AppMode>`；`:app` 订阅后决定内容区渲染哪个 feature |
| 播放状态 | 播放器实例**提升到 `:app`**（单例），切模式不销毁播放器 —— 直播可以挂着播，切到影视找片再切回来 |
| 返回栈 | 每个模式各有一条 `NavHost` 子图；切模式不重置各自子图，回来时恢复原位 |
| 焦点 | 切模式后焦点回到「模式开关」本身，而不是内容区第一项（避免用户下一按就误触） |

### 2.1 冷启动路径（关键路径，必须短）

```
Application.onCreate
   └─ AppStartDestination（读 DataStore + 一条 history 查询，均异步，但只等这两项）
         ├─ 合规未同意 → 提示页
         ├─ 无源        → 引导页
         └─ 否则        → 播放页（channelId 已就绪，立即 play()）
                            ├─ 首帧出画后：异步补台标 / 频道名 / EPG
                            └─ 失败：换线路 → 软解 → 停在播放页给出口
```

三条硬约束（对应 RULES §6.6）：

1. **关键路径只读两条数据**（`complianceAgreed`、`lastChannelId`），其余全部延后；
2. **不在启动路径上刷新源 / 拉 EPG** —— 这两件事交给 WorkManager 与播放页的后台任务；
3. **起播失败不许静默退回主页**：主页不是「安全兜底」，停在播放页给出口才是。

**为什么播放器实例在 `:app` 而不是 `:feature:iptv`**：启动要直接起播、切模式要不断流、从影视回直播要接着播，
三件事都要求播放器活过页面切换。放在 feature 里，页面一销毁播放器就没了，反而要重连、重缓冲。

## 3. 搜索：一个入口，两种口径

```
搜索框（IPTV 模式）
   │
   ├─→ ChannelSearchSource（本地 Room，同步，< 300ms）
   │
   └─→ VodSearchSource（远端多源并发）
             │
             ▼
      SearchRepository.search(query, scope = IPTV)
             │   ← 在这里按 IPTV_ALLOWED_TYPES 过滤（唯一防线）
             ▼
       UI 只拿到合法结果
```

- **白名单在 Repository 出口**，不在 ViewModel、不在 Composable。理由见 RULES §3.2：
  UI 会改、会复用、会被复制粘贴，Repository 的出口只有一个。
- `SearchScope` 只有两个值：`IPTV` / `VOD`。新增入口时必须显式选一个，**没有默认值**（编译器强制思考）。
- 结果用 `Flow` 流式返回：本地频道先出，远端逐源补入，UI 分两区渲染。

## 4. 源适配器（两套，一个接口）

直播源与影视源的形态完全不同（M3U/TXT vs 站点的 JSON 接口），但上层只关心「能拿到什么」：

```kotlin
interface LiveSourceAdapter {          // M3U / TXT / Xtream
    suspend fun load(source: SourceConfig): List<Channel>
}

interface VodSourceAdapter {           // 站点 JSON 规则 / JS 规则
    suspend fun categories(source: SourceConfig): List<Category>
    suspend fun list(source: SourceConfig, category: Category, page: Int): List<MediaItem>
    suspend fun detail(source: SourceConfig, id: String): MediaDetail
    suspend fun search(source: SourceConfig, keyword: String): List<MediaItem>
}
```

- 适配器实现全部在 `core:network`，按 `SourceConfig.type` 分发。
- **新增源格式 = 新增 Adapter**，不改上层 —— 这是整个项目最重要的可扩展点。
- **影视源配置格式与手机端共用一份**（D-03）：直接复用 `leimao-reader` 的 JSON 源规则与适配器实现。
  电视端独有的字段（列表默认排序、遥控器快捷键绑定等）一律作为**可选扩展字段**添加，
  缺省时不影响手机端解析；反向亦然，手机端新增字段电视端要能安全忽略。
  收益是两边源可互相导入、只维护一套适配器；代价是**任何一端改 schema 都必须同步另一端**，
  因此 schema 变更按「共用契约」对待，需要同时回归两端。

## 5. 数据存储（Room）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `source` | id, type(LIVE/VOD), url, ua, referer, enabled | 一个源一行；直播与影视同表不同 type |
| `channel` | id, sourceId, tvgId, name, group, logo, url, number | 频道；`(sourceId, name)` 唯一 |
| `channel_line` | channelId, url, quality | 同名频道的多线路（合并后） |
| `program` | channelId, start, stop, title, desc | EPG；按 start 建索引 |
| `media` | id, sourceId, type, title, poster, year, area | 影视条目；`type` 是白名单判断的依据 |
| `favorite` / `history` | targetId, targetType, positionMs, updatedAt | 收藏与播放进度（直播与点播共用一张表，靠 targetType 区分） |

**为什么 `type` 必须落库**：搜索白名单过滤依赖它。若只在解析时临时判断，换源或缓存命中时会漏。

## 6. 播放器封装

```kotlin
interface PlayerController {
    fun attach(view: PlayerView)
    fun play(url: String, headers: Map<String, String>, startMs: Long = 0)
    fun release()
    val state: StateFlow<PlaybackState>
}
```

- 默认实现 `Media3PlayerController`；未来接 VLC/IJK 时新增实现，不改调用方。
- 失败策略集中在封装里：**重试 → 换线路 → 软解 → 报错给用户**（四步降级，不让 UI 各写一遍）。

## 7. TV UI 的关键决策

| 决策 | 理由 |
|---|---|
| Compose for TV（不用 Leanback） | Leanback 的 Fragment + BrowseFragment 体系与 Compose 混用代价高；Compose for TV 提供 `Surface`/`Card` 的焦点态与 `TvLazyRow` 的焦点滚动 |
| 焦点视觉统一在 `core:designsystem` | 焦点是电视端的第一体验，不能各页面自己画描边 |
| 1080p 基准 + 字号缩放 | 电视观看距离 2~3m，14sp 是下限；缩放系数统一乘在 `Typography` 上 |
| 不用 ViewPager / 横向滑动切页 | 遥控器没有「滑」，横向切页在电视上是反模式 |

## 8. 目录结构（目标）

```
LEIMAOTV/
├─ app/                   # 组装层：只有 Activity / NavHost / 容器 / 路由级接线
│  ├─ src/main/           # 导航图、主页枢纽、合规提示、无源引导
│  ├─ src/debug/          # 演示源（example.com），正式包不含
│  └─ src/release/        # 同名空实现，保证 DebugSeed 在正式包是 no-op
├─ core/
│  ├─ model/              # 纯 Kotlin：Channel / ContentType / SearchScope / 白名单 / 启动落点
│  ├─ version/            # 纯 Kotlin：AppVersion / AppVersionNumber（版本号单一来源）
│  ├─ database/           # Room 实体 / DAO / ChannelRepository / StartupFactsReader
│  ├─ network/            # HttpClient / RequestHeaders / 解析器 / SourceAdapter 实现
│  ├─ player/             # PlayerController 与内核实现（M1 接 Media3）
│  └─ designsystem/       # TvTheme / TvTypography / FocusableCard / SafeArea
├─ feature/
│  ├─ iptv/  ├─ vod/  ├─ search/  ├─ settings/
├─ docs/
│  ├─ 功能清单.md
│  └─ 架构设计.md
├─ .github/workflows/     # CI：ktlint + 单测 + assembleDebug
├─ RULES.md
├─ CHANGELOG.md
├─ TODO.md
└─ README.md
```

**为什么 `core:model` 与 `core:version` 是纯 Kotlin（`kotlin-jvm`）而不是 Android 库**：
这两个模块承载的是「规则」——搜索白名单、启动落点、版本号公式。它们必须能被最普通的 JVM 单测
在毫秒级跑完，不该因为依赖 Android SDK 而被拖进 Robolectric 或真机。模块类型本身就是一条约束：
想在里面引 Android API 时，构建会直接拒绝。

**`:core:data` → `:core:version` 这条边（0.2.9.7 起）**：检查更新（SET-07）要拿「远端 tag」和
「本地 `CURRENT_VERSION`」比大小，而这个比较只有 `:core:version` 有一份。让 `:core:data` 引它，
而不是在数据层再写一遍版本解析 —— 两份解析会在某次「修订位补零 / 带 `v` 前缀」上分叉，
而分歧的表现是「更新器有时劝你升级到旧版」这种极难复现的问题。

## 9. 已定决策（M0 前拍板，2026-10-21）

| 问题 | 结论 | 代价 / 约束 |
|---|---|---|
| 最低支持的 Android 版本 | **minSdk 21（Android 5.0）**，向上兼容到 24+ | 覆盖 5.0 起的全部盒子（含 7.0+）；代价是 21~23 要单独维护兼容分支：通知渠道（26+ 才引入）、Scoped Storage（29+）之前的存储路径、TV 清单差异 |
| 是否内置软解内核 | **内置 VLC(libvlc)**，约 +20 MB | 老盒子硬解残缺时兜底；LGPL 要求**动态链接且可替换**（不得静态合并、需说明替换方式）；APK 体积红线仍为 ≤ 60 MB（RULES §7），M0 需实测 |
| 影视源配置格式 | **与手机端共用一份**（见 §4） | 电视端独有字段一律作可选扩展，不许破坏手机端解析；schema 变更视为「共用契约」，两端同时回归 |
| 开源许可证 | **Apache-2.0**（`LICENSE`） | 含专利授权；与 LGPL(VLC) 动态链接兼容；他人可商用但须保留声明与变更说明 |
